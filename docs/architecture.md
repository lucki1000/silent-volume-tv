# Architecture and HTTP API

## Why the two parts are needed

Changing the app alone does not stop a directly connected remote from sending
volume keys to Android. The bridge removes those two usages before the TV sees
them. The app receives the corresponding network commands and calls
`AudioManager.adjustStreamVolume(STREAM_MUSIC, direction, 0)`. The zero flags
avoid requesting the system volume UI, sound and vibration. They cannot suppress
a display independently generated by firmware or an external HDMI receiver.

See the Android [AudioManager reference](https://developer.android.com/reference/android/media/AudioManager#adjustStreamVolume(int,int,int))
for the underlying call. Devices reporting `isVolumeFixed()` return HTTP `409`
for volume changes; status reads still work.

The optional overlay uses an application-overlay window with no focus or touch
handling. It appears for two seconds after a successful network volume command.
Position and size preferences persist; rendering/permission failures do not fail
a volume command that has already succeeded.

The panel uses Android's display density, with an 8dp edge gap. It can sit on
either side at 75%, 100%, 125% or 150% size. A 4K panel may run its Android UI
at a lower resolution, so choose a size by how it looks on the TV. Some system
screens can hide application overlays even when permission is granted.

## BLE forwarding

One NimBLE stack owns both BLE roles. The bridge learns Report Map/Report Reference
descriptors and mirrors report IDs, sizes, types and available PnP metadata.
Callbacks enqueue work; discovery and forwarding run outside them. Filtering
interprets declared Consumer Control fields rather than searching raw bytes.

The descriptor limits are a 512-byte map, 16 report definitions, 512 bytes per
report, 1024 input fields and field widths up to 32 bits. Unsupported layouts are
rejected with a serial diagnostic. Reports too large for the TV's negotiated MTU
are blocked rather than truncated. Output/feature writes are queued back to the
remote; feature reads use a cache. The USB-powered bridge advertises 100% battery.

## Local API

Default listener: all local interfaces, TCP port **8090**. Every endpoint requires
`Authorization: Bearer <token>`. The app generates a persistent 128-bit random
token; rotating it requires updating the ESP's private header and firmware.

| Method | Path | Successful body | Overlay |
| --- | --- | --- | --- |
| `POST` | `/volume/up` | JSON state after one volume step | If enabled/permitted |
| `POST` | `/volume/down` | JSON state after one volume step | If enabled/permitted |
| `GET` | `/status` | JSON state | No |
| `GET` | `/volume/integer` | Current integer, without newline | No |

Example JSON:

```json
{"volume":6,"min":0,"max":15,"muted":false,"fixedVolume":false}
```

Requests use exact paths, no query string and no body. Read the device's `max`
rather than assuming a volume range. A successful command at a limit can leave
the value unchanged. No audio focus is requested.

`GET /volume/integer` returns `text/plain; charset=utf-8`, with no trailing
newline. Other successful responses are JSON; errors retain their status code
and JSON body. The app generates its 128-bit token locally and keeps it across
restarts. Rotating it reconfigures the listener immediately. Backups are disabled
to avoid transferring the token to another device.

| Status | Meaning |
| --- | --- |
| `400` | Malformed request, duplicate headers, or unsupported body/framing |
| `401` | Missing/incorrect token |
| `403` | Audio permission denied |
| `404` | Unknown path |
| `405` | Wrong method |
| `408` | Request read timeout |
| `409` | Fixed-volume device; up/down unavailable |
| `431` | Headers exceed 8 KiB |
| `503` | Audio unavailable, listener stopping, or queue busy |

The HTTP server uses two workers and an eight-request queue. Authentication does
not provide encryption; a device that can observe LAN traffic can see the token.

## Android lifecycle

The receiver is a foreground service. Enabled startup handles locked/unlocked
boot and package replacement; configuration lives in device-encrypted app storage.
Stopping the receiver persists a disabled state. Android force-stop, sleep and
vendor background policies can still interrupt service or networking. Open the
app once after installation and verify actual reboot behavior on the TV.

The boot actions are `LOCKED_BOOT_COMPLETED`, `BOOT_COMPLETED` and
`MY_PACKAGE_REPLACED`. Duplicate startup requests keep an existing listener.
`START_STICKY` asks Android to recreate a killed service. Turning off autostart
leaves an already running receiver active; **Stop receiver** persists a disabled
state. Network binding uses all local interfaces, so a Wi-Fi reconnect doesn't
require binding a new listener.

On updates from version 1.0, preferences migrate once from credential-protected
to device-protected storage after unlock, preserving the port, token and settings.
See Android's [Direct Boot guide](https://developer.android.com/privacy-and-security/direct-boot)
for the storage distinction.

The package/application ID remains `dev.silentvolume.tv`, and the version remains
1.5 (code 6). Updating an existing installation also requires the same signing
key. The repository deliberately contains no signing key or configured firmware.
